# skewbsimulator-solver
This project simulates a Skewb rubik's cube virtually, using custom functions to apply moves to the cube. The cube is represented by a 10-digit string, using a custom system to condense the information contained in all 14 pieces and 30 stickers into a 10-digit string. \
Rather than optimizing for readability or simplicity of functions in the simulation string, I've opted to create the shortest possible string to represent the skewb state, with the 10-character solve state string. This is because my goal is to generate a database with every combination of turns up to 10 on skewb, and the corresponding state. This system is outlined below. \
Optimizing for a shorter string to represent the cube makes the database much smaller on a large scale, since there are over 9,000,000 combinations I need to store. Thus, this approach makes more sense than a simpler approach that would take up much more storage. \
With this database, I can look up a given state and retrieve all solutions found in the database for it. This essentially functions as a Skewb solver, presenting you with every possible solution for the state you input. \
This is useful for generating solving algorithms, which are sequences of moves you memorize to solve certain states. This is useful so that speedsolvers can reduce to various states and know the fastest ways to solve from there. \
In skewb, solvers often identify multiple reductions to states that they know algorithms for, looking at various 'methods'. Essentially, the approach is to maximize the amount of 'methods' you know so you're more likely to find the best solution. Sometimes, it pays off to know multiple algorithms per case, depending on the context: the angle you get the case from, the last moves of your reduction (if your algorithm starts with the opposite move, you can do nothing instead of both), or ergonomics and flow. \
Thus, knowing multiple algorithms for a single state is a useful pursuit, in addition to being able to check multiple if you're trying to find one that's the best. This is why this database is particularly useful, because it stores every algorithm with its associated state, rather than every state with one associated algorithm. Thus, lookup by state will return multiple algorithms (often over 50), that you have options with. \



Simulator.py system: \
A base tag has the format of ABCDUV124, which is the solved state. Each corner sticker on a skewb corresponds to a letter, A-X. Rather than each corner piece represented, we use a common tactic from blind solving where you assign a letter to each sticker of the piece instead, to code for the orientation of the piece rather than just the piece itself. Additionally, similar to a traditional 3x3 blindfolded solve, we use the SPEFFZ color scheme to identify each corner's letter. \
Each corner represented in the tag indicates the position that each corner currently in the ABCDUV positions need to go. Thus, the solved state is defined by ABCDUV, since each corner there needs to go to the exact same spots that they're in to render a solved cube. \
A similar system is used for centers, using numbers 1-6. The top center is numbered 1, Front 2, Left 3, Back 4, Right 5, and Bottom 6. The numbers in the tag indicate where the pieces currently in slots 1,2,3 and 4 need to go to render solved state. Thus, a tag of 1234 would indicate the solved state. \
However, because of the unique notation used by skewb solvers at the top level, known as Rubikskewb notation, the center in the 3 spot doesn't move at all, as traditional moves are done around that piece, holding it constant, which is optimal for turning quickly. This means that 3 being solved is implied, since all possible moves used will not affect 3. Thus, the solved tag becomes 124. \
In addition to the solved tag ABCDUV124, the skewb can also be solved into a state where it's on the opposite side, for instance with blue in front instead of green. By nature, the skewb will only have 2 possible orientations to be solved in when assuming a fixed center like we do for center 3. Thus, we need to account for this and do it by also allowing CDABWX642 to also be considered solved. This is accopmlished by adding an additional function on top of the 4 moves for a z2 move, which in traditional notation, rotates the cube twice. Using this function, we can incorporate in our lookup to also find those. \
The other functions present apply each possible move of r, R, B, and b, and their counterclockwise counterparts to the string when called. There is also a function written to take a string of moves and reverse it, to have the opposite effect on the cube. This is accomplished simply by doing the moves in reverse order with the opposite move. \
